# AgentFlow 代码导读（Planner / Executor / Verifier / Generator）

> 目标：让你能对着源码看懂"四个模块各自吃什么、吐什么、怎么串起来"。
> 所有代码均摘自 `$AF_ROOT`（commit `b940064`），行号与源码一致。
> 原始文件副本在 `raw/` 目录（planner.py / executor.py / verifier.py / memory.py / formatters.py / solver.py）。
> 文中的「实测」来自我们在租用 GPU 上用真实 7B 模型跑出来的结果。

---

## 0. 先看全局：四个模块在哪

| 论文里的名字 | 代码里的位置 | 类 / 函数 | 一句话职责 |
|---|---|---|---|
| Planner（规划器） | `models/planner.py` | `class Planner` | 看题 + 看历史，决定"下一步用哪个工具、子目标是什么" |
| Executor（执行器） | `models/executor.py` | `class Executor` | 把"子目标"翻译成一行 Python 代码，并真正执行工具 |
| Verifier（检查器） | `models/verifier.py` | `class Verifier` | 看当前记忆够不够，输出 STOP / CONTINUE |
| **Generator（生成器）** | `models/planner.py` | `Planner.generate_final_output` / `generate_direct_output` / `generate_base_response` | **没有独立类**，就是 Planner 里最后写答案的几个方法 |
| 胶水（主循环） | `solver.py` | `class Solver.solve` | 按顺序调用上面四个，维护 Memory |
| 数据契约 | `models/formatters.py` | 4 个 pydantic 类 | 规定每个模块的输出长什么样 |
| 记忆 | `models/memory.py` | `class Memory` | 存每一步的 tool / sub_goal / command / result |

**最容易误会的一点**：论文图里画了四个模块，但代码里只有三个类（Planner / Executor / Verifier）。"Generator" 是 Planner 的三个生成方法，用的是 Planner 自己的引擎，不单独存在。

## 1. 数据契约：先搞清"每一步长什么样"

`models/formatters.py` 全文（40 行，建议先读它）：

```python
# Planner: QueryAnalysis        ← analyze_query 的输出
class QueryAnalysis(BaseModel):
    concise_summary: str
    required_skills: str
    relevant_tools: str
    additional_considerations: str

# Planner: NextStep             ← generate_next_step 的"理想输出"
class NextStep(BaseModel):
    justification: str
    context: str
    sub_goal: str
    tool_name: str

# Executor: MemoryVerification  ← 注意注释写的是 Executor，其实是 Verifier 用的
class MemoryVerification(BaseModel):
    analysis: str
    stop_signal: bool

# Executor: ToolCommand         ← generate_tool_command 的输出
class ToolCommand(BaseModel):
    analysis: str
    explanation: str
    command: str
```

这四个类就是四个模块之间的"接口"。**但要注意：接口只是"期望"，模型不一定照做**——我们后面会看到 7B 模型经常返回纯文本，代码只能靠正则去抠。

## 2. 主循环：谁在什么时候调用谁

`solver.py:89-172`（精简后，保留全部关键动作）：

```python
step_count = 0
while step_count < self.max_steps and (time.time() - query_start_time) < self.max_time:
    step_count += 1

    # [2] Planner：决定下一步
    next_step = self.planner.generate_next_step(
        question, image_path, query_analysis, self.memory, step_count, self.max_steps, json_data
    )
    context, sub_goal, tool_name = self.planner.extract_context_subgoal_and_tool(next_step)

    if tool_name is None or tool_name not in self.planner.available_tools:
        # 工具名非法：不调用 executor，直接编一条假结果
        command = "No command was generated because the tool was not found."
        result  = "No result was generated because the tool was not found."
    else:
        # [3] Executor：生成代码
        tool_command = self.executor.generate_tool_command(
            question, image_path, context, sub_goal, tool_name,
            self.planner.toolbox_metadata[tool_name], step_count, json_data
        )
        analysis, explanation, command = self.executor.extract_explanation_and_command(tool_command)

        # [4] Executor：执行工具
        result = self.executor.execute_tool_command(tool_name, command)
        result = make_json_serializable_truncated(result)

    # [5] 先写记忆
    self.memory.add_action(step_count, tool_name, sub_goal, command, result)

    # [6] 再验证
    stop_verification = self.verifier.verificate_context(
        question, image_path, query_analysis, self.memory, step_count, json_data
    )
    context_verification, conclusion = self.verifier.extract_conclusion(stop_verification)

    if conclusion == 'STOP':
        break

# 循环结束后才生成最终答案
final_output  = self.planner.generate_final_output(question, image_path, self.memory)   # Generator
direct_output = self.planner.generate_direct_output(question, image_path, self.memory)  # Generator
```

四个关键顺序，值得记住：

1. **Planner 先跑**，产出三元组；
2. **Executor 跑两次**（先生成代码，再执行代码）；
3. **Memory 先写、Verifier 后验**——所以 verifier 永远看到"最新那一步"；
4. **Generator 在循环外**，只跑一次，输入只有 memory。

## 3. Planner：两个引擎、两次调用

### 3.1 构造函数：一个"可训练"，一个"固定"

`models/planner.py:13-27`：

```python
class Planner:
    def __init__(self, llm_engine_name, llm_engine_fixed_name="gpt-4o", ...):
        self.llm_engine_name = llm_engine_name
        self.llm_engine_fixed_name = llm_engine_fixed_name
        ...
        self.llm_engine_fixed = create_llm_engine(model_string=llm_engine_fixed_name, ...)
        self.llm_engine       = create_llm_engine(model_string=llm_engine_name, ...)
```

- `llm_engine`（main）：用来**做规划**（下一步用哪个工具），对应论文里被训练的那个 7B；
- `llm_engine_fixed`（fixed）：用来**分析题目**和**写最终答案**，论文里是没训练的 instruct 模型。

一句话：**同一个类里塞了两个模型**，一个负责"决策"，一个负责"读题 + 写答案"。

### 3.3 `generate_next_step`：每轮都跑，真正的"决策"

`models/planner.py:185-291`（文本版 prompt，258-285 行）：

```python

**这就是老师问的"planner 的输入"**，一共五块：

| 块 | 来源 | 说明 |
|---|---|---|
| Query | 原始题目 | 测试脚本会把 `task_description` 拼在前面 |
| Query Analysis | 3.2 的输出 | 一次性生成，之后每轮重复 |
| Available Tools | `enabled_tools` 映射后的名单 | 就是 action 的取值范围 |

> 实测：这段 prompt 长度 **7,272–7,779 字符**（每轮都在涨）。

### 3.4 `extract_context_subgoal_and_tool`：把模型输出"抠"成三元组

`models/planner.py:130-183`：

```python
def extract_context_subgoal_and_tool(self, response):
    def normalize_tool_name(tool_name):        # 空格/下划线/大小写归一化
        ...
    try:
        if isinstance(response, str):
            try:
                response_dict = json.loads(response)      # 先试 JSON
                response = NextStep(**response_dict)
            except Exception as e:
                print(f"Failed to parse response as JSON: {str(e)}")

        if isinstance(response, NextStep):
            context  = response.context.strip()
            sub_goal = response.sub_goal.strip()
            tool_name = response.tool_name.strip()
        else:
            text = response.replace("**", "")             # 去掉 markdown 加粗
            pattern = r"Context:\s*(.*?)Sub-Goal:\s*(.*?)Tool Name:\s*(.*?)\s*(?:```)?\s*(?=\n\n|\Z)"
            matches = re.findall(pattern, text, re.DOTALL)
            context, sub_goal, tool_name = matches[-1]    # 取最后一组
        tool_name = normalize_tool_name(tool_name)
    except Exception as e:
        return None, None, None                            # 解析失败 → 全 None
    return context, sub_goal, tool_name
```

实测（真实 7B 的输出）：

```
**Justification:** The problem involves basic arithmetic...
**Context:** 
- Initial number of book copies: 48
- Books sold on Monday: \( \frac{3}{8} \times 48 \)
**Sub-Goal:** Calculate the remaining number of book copies...
**Tool Name:** Python_Code_Generator_Tool
```

日志里先打印 `Failed to parse response as JSON`，再打印 `arielg 2`（源码里遗留的调试输出），最后成功抽出三元组——**说明结构化输出没生效，靠的是正则**。

> 为什么没生效？因为 vLLM / DashScope 引擎**忽略 `response_format`**（`engine/vllm.py:99-130` 里根本没使用这个参数）。只有 GPT-4o 走 OpenAI 的结构化输出才会真的返回对象。

## 4. Executor：把"子目标"编译成一行代码

### 4.1 `generate_tool_command`：第二次 LLM 调用

`models/executor.py:82-126`（prompt 中段省略）：

```python
def generate_tool_command(self, question, image, context, sub_goal, tool_name, tool_metadata, ...):
    prompt_generate_tool_command = f"""
    Task: Generate a precise command to execute the selected tool.

Context:
- **Query:** {question}
- **Sub-Goal:** {sub_goal}
- **Tool Name:** {tool_name}
- **Tool Metadata:** {tool_metadata}
- **Relevant Data:** {context}

Instructions:
1.  Analyze the tool's required parameters from its metadata.
2.  Construct valid Python code that addresses the sub-goal using the provided context and data.
3.  The command must include at least one call to `tool.execute()`.
4.  Each `tool.execute()` call must be assigned to a variable named **`execution`**.
5.  Please give the exact numbers and parameters should be used in the `tool.execute()` call.
"""
    tool_command = self.llm_generate_tool_command(prompt_generate_tool_command, response_format=ToolCommand)
```

注意：这一步用的引擎是 **`self.llm_generate_tool_command`**，也就是构造时传进来的 `executor_engine`——和 planner 不是一个模型实例。

**这就是"planner 以什么形式进入执行器"的答案**：planner 的三元组（context / sub_goal / tool_name）被拼进**上面这段新 prompt**，交给另一个模型写代码。所以：

- 传过去的是**结构化字段**（不是 plan，也不是 planner 的原始输出）；
- executor 再把它变成**一段 prompt**；
- 最终产物是**一行 Python 代码**。

实测（书店题）：

```python
execution = tool.execute(query="A bookstore had 48 copies. It sold 3/8 on Monday and 12 on Tuesday. How many are left?")
```

> 值得注意：executor **没有用 sub_goal**，而是把原题整段塞进 query。三元组虽然传了，但被"浅加工"了。

### 4.3 `execute_tool_command`：真正执行（这里有两个大坑）

`models/executor.py:191-330`（核心 204-256、307-328）：

```python
def split_commands(command):
    # 只认单行的 execution = tool.execute(...)
    pattern = r'.*?execution\s*=\s*tool\.execute\([^\n]*\)\s*(?:\n|$)'
    return [b.strip() for b in re.findall(pattern, command, re.DOTALL) if b.strip()]

def execute_with_timeout(block, local_context):
    result_container = {...}
    cancel_event = threading.Event()
    def target():
        try:
            local_context['_cancel_event'] = cancel_event
            exec(block, globals(), local_context)            # ← 直接 exec
            result_container['result'] = local_context.get('execution')
        except Exception as e:
            result_container['exception'] = e
    exec_thread = threading.Thread(target=target, daemon=True)
    exec_thread.start()
    exec_thread.join(timeout=self.max_time)                  # ← 超时保护
    ...
    return result_container['result']

# ...
tool = self.tool_instances_cache.get(tool_name) or 动态 import
tool.set_custom_output_dir(self.query_cache_dir)
for block in split_commands(command):
    result = execute_with_timeout(block, {'tool': tool})
```

两个坑：

1. **`split_commands` 保留的是"调用行 + 它之前的代码"**。正则开头的 `.*?` 会把 `execution = tool.execute(...)` 前面的语句一起带上，但**调用之后的语句会被丢掉**；如果整段代码里根本没有 `execution = tool.execute(...)`（例如模型只写了函数定义），则一块都匹配不到，等于什么都没执行（返回空列表）。

   实测三种写法（`regex_test.py`）：

   | 模型的代码 | 匹配结果 |
   |---|---|
   | `execution = tool.execute(query="a")` | 1 块，就是这一行 |
   | `x = 48*3/8` + `execution = tool.execute(...)` + `print(x)` | 1 块，**包含前两行**，`print(x)` 被丢 |
   | 只有 `def f(x): return x` | **0 块**，什么都不执行 |

2. **`exec` 执行任意代码**，只靠线程超时兜底（`max_time` 秒），没有沙箱。

实测（Iceland 那题）：
- 第 1 步：命令行匹配到了，但工具内部生成的 Python 有缩进错误 → `{"error": "unexpected indent (<string>, line 24)"}`；
- 第 2/3 步：命令行同样匹配到了，但工具内部只生成了一个 `is_prime` 函数定义、没有调用 → `{"printed_output": "", "variables": {"is_prime": "<function: is_prime>"}}`。

也就是说：**工具确实"跑了"，但工具内部生成的程序并不完整（只有定义、没有计算）**——这是代码层面一个很实际的信息丢失点。

### 5.2 `extract_conclusion`：STOP 到底怎么判出来的

`models/verifier.py:147-178` 全文：

```python
def extract_conclusion(self, response):
    if isinstance(response, str):
        try:
            response = MemoryVerification(**json.loads(response))
        except Exception as e:
            print(f"Failed to parse response as JSON: {str(e)}")

    if isinstance(response, MemoryVerification):
        analysis = response.analysis
        stop_signal = response.stop_signal
        if stop_signal:
            return analysis, 'STOP'
        else:
            return analysis, 'CONTINUE'
    else:
        analysis = response
        pattern = r'conclusion\**:?\s*\**\s*(\w+)'
        matches = list(re.finditer(pattern, response, re.IGNORECASE | re.DOTALL))
        if matches:
            conclusion = matches[-1].group(1).upper()
            if conclusion in ['STOP', 'CONTINUE']:
                return analysis, conclusion

        # 最后兜底：全文搜子串
        if 'stop' in response.lower():
            return analysis, 'STOP'
        elif 'continue' in response.lower():
            return analysis, 'CONTINUE'
        else:
            print("No valid conclusion (STOP or CONTINUE) found in the response. Continuing...")
            return analysis, 'CONTINUE'
```

结构化的对象（`stop_signal: bool`）只在 GPT-4o 那条路径上存在；7B/vLLM 返回文本时，走的是正则 + 子串兜底。

**实测（AMC23 那题）**，verifier 的真实输出是：

```
### Conclusion:
Since all parts of the query have been addressed...
**Final Determination: STOP**
```

解析过程：
1. 正则找 `conclusion` → 命中 `### Conclusion:`，取下一个词 → `"Since"`，不是 STOP/CONTINUE；
2. 继续找，命中 `This conclusion ensures...` → `"ensures"`，仍然不是；
3. 正则失败 → **全文搜 `stop`** → 命中 `"STOP"` → 判 STOP。

所以这次"答对了"是**靠字符串里恰好出现 STOP**。如果模型写 `"I would not stop here"`，同样会被判 STOP（我离线验证过）。

## 7. Memory：模块之间真正的"载体"

`models/memory.py:65-82`：

```python
def add_action(self, step_count, tool_name, sub_goal, command, result):
    action = {
        'tool_name': tool_name,
        'sub_goal': sub_goal,
        'command': command,
        'result': result,
    }
    step_name = f"Action Step {step_count}"
    self.actions[step_name] = action

def get_actions(self):
    return self.actions
```

**只有四个字段**。这就是为什么：

- planner 看不到 verifier 的 analysis（verifier 不往 memory 写）；
- planner 看不到 executor 的 analysis/explanation（只留了 command）；
- planner 看不到 justification（压根没存）。

## 8. 把四个模块串起来

```
题目 question
   │
   ├─(1)─ Planner.analyze_query(fixed) ──→ query_analysis 字符串
   │
   ▼ 循环
   ├─(2)─ Planner.generate_next_step(main) ──→ NextStep / 文本
   │        └─ extract → (context, sub_goal, tool_name)
   │
   ├─(3)─ Executor.generate_tool_command ──→ ToolCommand{analysis, explanation, command}
   │        └─ extract → command（一行 Python）
   │
   ├─(4)─ Executor.execute_tool_command ──→ result（JSON）
   │        └─ exec(split_commands(command)) + tool.execute()
   │
   ├─(5)─ Memory.add_action(tool, sub_goal, command, result)
   │
   ├─(6)─ Verifier.verificate_context(fixed) ──→ MemoryVerification / 文本
   │        └─ extract_conclusion → STOP / CONTINUE
   │
   └─ STOP? ── 否 → 回到 (2)
              └─ 是 → 跳出
   │
   ├─(7)─ Planner.generate_final_output(fixed)  ──→ final_output
   └─(8)─ Planner.generate_direct_output(fixed) ──→ direct_output
```

每一步传的"对象"：

| 步骤 | 传递的东西 | 类型 |
|---|---|---|
| (1)→(2) | `query_analysis` | str |
| (2)→(3) | `context, sub_goal, tool_name` | 3 × str |
| (3)→(4) | `command` | str（Python 源码） |
| (4)→(5) | `result` | list/dict（工具返回值） |
| (5)→(6) | `memory.get_actions()` | dict |
| (6)→(2) | **只有 STOP/CONTINUE 这个二值**（通过 `break`） | bool |
| (5)→(7)(8) | `memory` | dict |
