# AgentFlow 三问回答稿（基于真实复现实验）

> 复现环境：AutoDL 单卡 RTX 4090D 24G；vLLM 0.11.0；planner = 作者权重 `AgentFlow/agentflow-planner-7b`（fp32→bf16）；executor / verifier / planner_fixed = DashScope `qwen-plus`；工具 = OpenAI `gpt-4o-mini`（Generalist / Wikipedia / Python）。
> 声明：**只做推理评测，没有训练**。所有数字都是"作者训练好的 planner 的零样本表现"，不是 Flow-GRPO 训练结果。

---

## 0. 三问速览

| 问题 | 一句话回答 |
|---|---|
| Planner 的输入是什么 | 两次调用：①审题 = 题目 + 工具名单 + 工具说明；②决策 = 题目 + 审题结果 + 工具名单 + 工具说明 + **全部历史记忆** + 步数 |
| Planner 以什么形式进入执行器 | 不是 plan、也不是 planner 的原始 prompt，而是**三元组 `(context, sub_goal, tool_name)`**；执行器把它重新拼成自己的 prompt，让模型写出一行 `execution = tool.execute(...)` |
| Verifier 输出什么、可信吗、什么进下一轮 | 输出 `(analysis, STOP/CONTINUE)`；**只有二值影响循环**；analysis 不进下一轮；判断只基于记忆文本，靠正则/子串兜底，**不可信** |

## 1. Planner 的输入与输出

### 1.1 一个类，两个引擎，两次调用

`models/planner.py:13-27` 里创建了两个引擎：

```python
self.llm_engine_fixed = create_llm_engine(model_string=llm_engine_fixed_name, ...)   # 辅助脑
self.llm_engine       = create_llm_engine(model_string=llm_engine_name,       ...)   # 决策脑（作者权重）
```

| 调用 | 函数 | 时机 | 次数 | 用哪个引擎 |
|---|---|---|---|---|
| 审题 | `analyze_query` | 循环之前 | 每题 1 次 | fixed |
| 决策 | `generate_next_step` | 每一轮（含第 1 轮） | 最多 max_steps 次 | main |

所以"第 1 轮"其实调了两次 planner：先审题，再决策；第 2 轮开始才只调决策。

### 1.2 审题的输入与输出

输入三块：

```text
- Query: {题目}
- Available tools: ['Generalist_Solution_Generator_Tool', 'Python_Code_Generator_Tool', ...]
- Metadata for tools: {每个工具的完整说明}
```

输出是四字段的审题结果：

```text
Concise Summary: 这题在问什么
Required Skills: 需要什么能力
Relevant Tools: 可能用到哪些工具
Additional Considerations: 还要注意什么
```

这段文字被转成字符串存进 `json_data["query_analysis"]`，**之后每一轮都原样再贴给决策脑**。

### 1.3 决策的输入：五块

`planner.py:258-266` 的 f-string：

```python
prompt = f"""
- **Query:** {question}
- **Query Analysis:** {query_analysis}
- **Available Tools:** {self.available_tools}
- **Toolbox Metadata:** {self.toolbox_metadata}
- **Previous Steps:** {memory.get_actions()}
"""
```

实测构成（书店题，2 个工具，总计 **7,272 字符 / 56 行**）：

| 段落 | 字符数 | 占比 | 每轮变不变 |
|---|---:|---:|---|
| 任务说明 | 110 | 2% | 不变 |
| **题目 Query** | **110** | **2%** | 不变 |
| 审题 Query Analysis | 1,916 | 26% | 不变 |
| 工具名单 | 68 | 1% | 不变 |
| **工具说明书 Metadata** | **4,090** | **56%** | 不变（每轮重复） |
| 历史 Previous Steps | 2 | 0% | **每轮变长** |
| 指令/格式/规则 | 843 | 12% | 不变 |

**三个观察**：

1. 真正属于"这道题"的只有 110 字符，其余 98% 是模板、说明书、格式要求；
2. 工具说明书每轮完整重贴（约 4,000 字符），10 轮就是 40,000 字符的重复；
3. 历史每轮线性增长：实测第 1 轮 5,584 字符 → 第 2 轮 6,038 → 第 3 轮 6,813。

### 1.4 决策的输出：文本，不是对象

代码期望：

```python
class NextStep(BaseModel):
    justification: str
    context: str
    sub_goal: str
    tool_name: str
```

调用时也带了 `response_format=NextStep`，但 **vLLM / DashScope 引擎会忽略这个参数**（`engine/vllm.py` 里根本没使用它），返回的是纯文本。

真实输出：

```text
**Justification:** The problem involves basic arithmetic operations...
**Context:** 
- Initial number of book copies: 48
- Books sold on Monday: \( \frac{3}{8} \times 48 \)
**Sub-Goal:** Calculate the remaining number of book copies after sales on Monday and Tuesday.
**Tool Name:** Python_Code_Generator_Tool
```

### 1.5 解析：正则抠出三个字段

`planner.py:166-176`：

```python
text = response.replace("**", "")
pattern = r"Context:\s*(.*?)Sub-Goal:\s*(.*?)Tool Name:\s*(.*?)\s*(?:```)?\s*(?=\n\n|\Z)"
matches = re.findall(pattern, text, re.DOTALL)
context, sub_goal, tool_name = matches[-1]
```

- 先试 `json.loads`（失败，日志打印 `Failed to parse response as JSON`）；
- 再走上面的正则（日志打印源码里遗留的 `arielg 2`）；
- **`justification` 在这一步被丢弃**。

### 1.6 Planner 看得到 / 看不到什么

| 看得到 | 看不到 |
|---|---|
| 原始题目 | Verifier 的分析（不存） |
| 审题结果 | Executor 的 analysis/explanation（不存） |
| 工具名单 + 完整工具说明 | 自己上一步的 justification（丢弃） |
| memory 里全部历史（四个字段） | 工具内部过程（只有 result，且截断到 10 万字符） |
| 当前步数/最大步数 | 图像（`is_multimodal` 默认关，且引擎构造时硬编码 False） |

**关键**：Planner 的"世界" = 题目 + 一次审题 + 工具说明书 + 一本只记四样东西的流水账。

## 2. Planner 如何进入执行器

### 2.1 传递物：三元组，不是 plan

`solver.py:104`：

```python
context, sub_goal, tool_name = self.planner.extract_context_subgoal_and_tool(next_step)
```

所以到执行器手里的只有三个字符串：

- `context`：给工具用所需的数据/文件名/变量；
- `sub_goal`：这一步要达成什么；
- `tool_name`：动作标签。

**不是多步 plan**（没有步骤列表），**也不是 planner 的 prompt**（没有原样传递）。

### 2.2 执行器把它们重新拼成新 prompt

`executor.py:82-119`：

```text
Task: Generate a precise command to execute the selected tool.

Context:
- **Query:** ...
- **Sub-Goal:** ...
- **Tool Name:** ...
- **Tool Metadata:** ...
- **Relevant Data:** {context}

Instructions:
3.  The command must include at least one call to `tool.execute()`.
4.  Each `tool.execute()` call must be assigned to a variable named **`execution`**.
```

实测长度 4,057 字符。**注意：执行器的输入里没有历史**——它不知道上一步为什么失败。

### 2.3 执行器 LLM 的产物：一行 Python

```python
execution = tool.execute(query="Harry Flashman nationality Royal Flash film")
```

这行的含义：

| 部分 | 含义 |
|---|---|
| `execution` | 约定的变量名，执行器靠它取结果 |
| `tool` | 工具实例（这一轮 Planner 选了 Wikipedia，就把 Wikipedia 实例绑定成 `tool`） |
| `.execute(...)` | 工具真正干活的方法 |
| `query="..."` | 参数；这三个工具都只接受一个 `query` 字符串（Web_RAG 还要 url） |

### 2.4 执行：切代码 + exec

`solver.py:136` 调用 `execute_tool_command`，内部三步：

```python
# 1) 切出调用行（连同它之前的辅助代码）
pattern = r'.*?execution\s*=\s*tool\.execute\([^\n]*\)\s*(?:\n|$)'

# 2) 执行
exec(block, globals(), {'tool': tool})
result = local_context.get('execution')

# 3) 返回结果列表
```

实测的三种情况：

| 模型写的代码 | 切出的块 | 结果 |
|---|---|---|
| 单行 `execution = tool.execute(...)` | 1 块 | 正常 |
| `x = ...` + 调用 + `print(x)` | 1 块（含前两行，`print(x)` 丢） | 正常 |
| 只有函数定义（没有 `execution=`） | **0 块** | `[]`，什么都没执行 |

### 2.5 必须区分 command 和 result（最易错）

| 字段 | 是什么 | 谁产生 | 存哪 |
|---|---|---|---|
| `command` | `execution = tool.execute(...)` 这行代码 | 执行器 LLM | `action['command']` |
| `result` | 工具执行后的返回值 | 工具 | `action['result']` |

`memory.py:65`：

```python
action = {
    'tool_name': tool_name,
    'sub_goal': sub_goal,
    'command': command,
    'result': result,
}
```

### 2.6 真实的 result 长什么样

Wikipedia 工具返回：

```json
{
  "query": "Harry Flashman nationality Royal Flash film",
  "relevant_pages": [],
  "other_pages (may be irrelevant to the query)": [
    {"title": "Harry Flashman", "url": "https://en.wikipedia.org/wiki/Harry_Flashman", "abstract": "..."},
    {"title": "Lola Montez", "url": "https://en.wikipedia.org/wiki/Lola_Montez", "abstract": "..."}
  ]
}
```

工具内部其实是一整条流水线：维基搜索 → LLM 选相关页面 → 抓正文 → RAG 压缩。但**实测这条流水线在我们的环境里断在第二步**：三个多跳数据集共 **86 次工具调用，`relevant_pages` 全部为空，`retrieved_information` 一次都没产生**。

原因是"选相关页面"依赖结构化输出：

```python
response = llm_engine.generate(prompt, response_format=Select_RelevantQueries)
matched_queries = response.matched_queries      # 期望对象
```

而我们的引擎忽略 `response_format`，返回字符串 → 没有 `.matched_queries` → 异常 → 返回空列表。

**结论**：多跳实验中 Wikipedia 只返回了搜索标题/摘要，模型主要靠参数记忆答题，不是检索。

## 3. Verifier 的输出与可信度

### 3.1 输入：五块

```text
Task: Evaluate if the current memory is complete and accurate enough...
Context:
- **Query:** ...
- **Available Tools:** ...
- **Toolbox Metadata:** ...
- **Initial Analysis:** ...
- **Memory (Tools Used & Results):** {'Action Step 1': {...}, ...}
Final Determination:
- 够 → 以 "STOP" 结尾
- 不够 → 以 "CONTINUE" 结尾
```

它看到的和 Planner 几乎一样，**区别是没有标准答案、没有工具中间日志**。

### 3.2 输出：对象或文本

期望 `MemoryVerification{analysis, stop_signal}`；实际因为引擎忽略 `response_format`，返回的是文本（一大段分析 + 一句结论）。

### 3.3 解析：四级兜底

`verifier.py:147-178`：

```python
# 1) 能解析成对象 → 直接读 stop_signal
# 2) 否则正则找 "conclusion: XXX"，取最后一个
pattern = r'conclusion\**:?\s*\**\s*(\w+)'
# 3) 都不行 → 全文搜子串
if 'stop' in response.lower(): return analysis, 'STOP'
elif 'continue' in response.lower(): return analysis, 'CONTINUE'
# 4) 都没有 → 默认 CONTINUE
```

### 3.4 实测案例

| 模型输出 | 实际解析路径 | 结果 | 是否正确 |
|---|---|---|---|
| `Conclusion: STOP` | 正则命中 | STOP | ✅ |
| `### Conclusion:\nSince ...\n**Final Determination: STOP**` | 正则拿到 "Since" → 子串 `stop` | STOP | ✅（碰巧） |
| `I would not stop here` | 子串 `stop` | STOP | ❌ |
| 空响应 / 报错 dict | 都不命中 | CONTINUE | 兜底 |

### 3.5 三个结论

1. **它判断的是"记忆是否足够"，不是"答案是否正确"**：不重算、不比对、不检查工具是否报错；
2. **解析很脆**：`stop` 这个词出现在任何地方都能触发 STOP；
3. **结论不回写**：`analysis` 只存进 `json_data` 供日志查看，不进 memory，所以下一轮 Planner 完全不知道 Verifier 说了什么。

补充一个实现缺陷：`verificate_context` 只调用 `self.llm_engine_fixed`，而它被绑成 `planner_fixed`，所以 **`model_engine[2]`（verifier 配置）实际无效**——改它不会改变 verifier 行为。

### 3.6 它在循环里的真实作用

`solver.py:171`：

```python
if conclusion == 'STOP':
    break
```

只有这一处使用。也就是说 Verifier 对系统的影响**只有"停/不停"**，没有任何"下一轮该怎么做"的信息。

|---|---|

### 4.3 从数据能得出的结论

1. **决定成败的是执行器**：全底座 0/10、全作者 0/10；把执行器换成 qwen-plus 后，两组都到 5–6/10；
2. **作者 planner 相对 Qwen planner 没有显著优势**：AIME 6 vs 5、20 题 8 vs 8、多跳 13 vs 11、B 组 41 vs 41，差异都在 1–2 题内；
3. 全作者配置（B）最差，因为让 planner 兼职写代码，而它没被训练做这件事。

## 5. 局限

1. **未训练**，只评测作者权重；
2. 单卡 24G，无法同时部署 planner 和官方执行器，用 qwen-plus 代替 qwen2.5-7b-instruct；
3. 缺 Google 搜索（Gemini key 随 Google 账号停用），搜索类数据集只能用维基；
4. **Wikipedia 检索在本环境失效**（86 次调用 relevant_pages 全空），多跳成绩不代表检索能力；
5. 样本 10–20 题，置信区间宽；
6. OpenAI 依赖本机反向隧道，稳定性受限；
7. 评分器为宽松匹配（子串/字母），非官方脚本。
