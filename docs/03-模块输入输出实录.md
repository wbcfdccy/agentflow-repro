# AgentFlow 模块输入输出实录

> 目的：用**真实运行的输入/输出**回答老师提出的四个问题，而不是只讲代码。
> 环境：AutoDL 单卡 RTX 4090D 24G；vLLM 0.11.0；planner = 作者权重 `AgentFlow/agentflow-planner-7b`（fp32→bf16）；executor / verifier / planner_fixed = DashScope `qwen-plus`；工具 = OpenAI `gpt-4o-mini`（Generalist / Wikipedia / Python）。
> **重要声明：我们只做了推理评测，没有训练。** 所有数字都是"作者训练好的 planner 的零样本表现"，不是 Flow-GRPO 训练结果。

---

## 0. 一句话总览

| 模块 | 输入 | 输出 | 二者之间传的是什么 |
|---|---|---|---|
| Planner | 题目 + 审题结果 + 工具名单 + 工具说明书 + **全部历史** | 一段固定格式的**文本** | 正则解析成三元组 `(context, sub_goal, tool_name)` |
| Executor | 题目 + 三元组 + 该工具的 metadata | 一行 Python 代码 + 执行结果 | `command` 字符串 → `result` |
| Verifier | 题目 + 审题结果 + 工具说明 + **全部历史** | `MemoryVerification{analysis, stop_signal}` 或文本 | 解析成 `STOP` / `CONTINUE` |
| Generator | 题目 + **全部历史**（+ 审题结果） | 最终答案文本 | 无（终点） |

---

## 1. Planner

### 1.1 什么时候被调用

| 调用 | 函数 | 次数 | 引擎 |
|---|---|---|---|
| 审题 | `analyze_query` | 每题 **1 次**（循环之前） | fixed（辅助脑） |
| 决策 | `generate_next_step` | **每一轮**（含第 1 轮） | main（决策脑 = 作者权重） |

### 1.2 输入：真实 prompt 的构成

实测总长度 **7,272 字符 / 56 行**（书店题，2 个工具）：

| 段落 | 字符数 | 占比 | 每轮变不变 |
|---|---:|---:|---|
| 任务说明 | 110 | 2% | 不变 |
| **题目 Query** | **110** | **2%** | 不变 |
| 审题 Query Analysis | 1,916 | 26% | 不变 |
| 工具名单 | 68 | 1% | 不变 |
| **工具说明书 Metadata** | **4,090** | **56%** | 不变（每轮重复） |
| 历史 Previous Steps | 2 | 0% | **每轮变长** |
| 指令/格式/规则 | 843 | 12% | 不变 |

原文片段：

```text
Task: Determine the optimal next step to address the query using available tools and previous steps.

Context:
- **Query:** A bookstore had 48 copies. It sold 3/8 on Monday and 12 on Tuesday. How many are left? Answer with the number.
- **Query Analysis:** ### Summary of the Query ...
- **Available Tools:** ['Generalist_Solution_Generator_Tool', 'Python_Code_Generator_Tool']
- **Toolbox Metadata:** {'Generalist_Solution_Generator_Tool': {'tool_name': ..., 'input_types': {...}, 'demo_commands': [...], 'user_metadata': {'limitation': ..., 'best_practice': ...}}, ...}
- **Previous Steps:** {}
```

**结论**：真正属于"这道题"的只有 110 字符；98% 是模板、说明书和格式要求。

### 1.3 输出：模型原文 → 三元组

模型实际输出（markdown，不是 JSON）：

```text
**Justification:** The problem involves basic arithmetic operations...
**Context:** 
- Initial number of book copies: 48
- Books sold on Monday: \( \frac{3}{8} \times 48 \)
**Sub-Goal:** Calculate the remaining number of book copies after sales on Monday and Tuesday.
**Tool Name:** Python_Code_Generator_Tool
```

代码先试 `json.loads`（失败，日志打印 `Failed to parse response as JSON`），再走正则（日志打印 `arielg 2`）：

```python
text = response.replace("**", "")
pattern = r"Context:\s*(.*?)Sub-Goal:\s*(.*?)Tool Name:\s*(.*?)\s*(?:```)?\s*(?=\n\n|\Z)"
context, sub_goal, tool_name = re.findall(pattern, text, re.DOTALL)[-1]
```

得到：

```
context   = "- Initial number of book copies: 48 ..."
sub_goal  = "Calculate the remaining number of book copies..."
tool_name = "Python_Code_Generator_Tool"
```

**`justification` 被丢弃。**

### 1.4 第二轮多了什么

第二轮 prompt（同题）变成 6,038 字符，多出来的只有这一块：

```text
- **Previous Steps:** {'Action Step 1': {'tool_name': 'Python_Code_Generator_Tool',
    'sub_goal': "Generate a Python script that finds the 100th prime ...\n\n4.",
    'command': 'execution = tool.execute(query="...")',
    'result': [{'error': 'unexpected indent (<string>, line 24)'}]}}
```

三个实测异常：

1. 报错信息**确实**进了状态（`result.error`）；
2. `sub_goal` 尾部粘了 `\n\n4.`——正则把模型输出的列表编号吞进了内容；
3. 模型仍然选同一个工具（三轮都是 Python），说明未训练/训练不足的策略不会利用"报错"这个状态。

## 2. Executor

### 2.1 输入：真实 prompt（4,057 字符）

```text
Task: Generate a precise command to execute the selected tool.

Context:
- **Query:** A bookstore had 48 copies...
- **Sub-Goal:** Calculate the remaining number of book copies after sales on Monday and Tuesday.
- **Tool Name:** Python_Code_Generator_Tool
- **Tool Metadata:** {'tool_description': ..., 'input_types': {'query': 'str - ...'}, 'demo_commands': [...]}
- **Relevant Data:** - Initial number of book copies: 48 ...

Instructions:
3.  The command must include at least one call to `tool.execute()`.
4.  Each `tool.execute()` call must be assigned to a variable named **`execution`**.
```

**关键**：Executor 的输入里**没有历史**，它不知道上一步为什么失败。

### 2.2 输出：代码 + 解析

模型输出（未按三段式，所以解析退化）：

```text
Generated Command:
```python
execution = tool.execute(query="A bookstore had 48 copies. It sold 3/8 on Monday and 12 on Tuesday. How many are left?")
```
```

解析结果：

```
[Analysis]: No analysis found.
[Explanation]: No explanation found.
[Command]: execution = tool.execute(query="A bookstore had 48 copies...")
```

**实测问题**：`sub_goal` 明明写的是"计算剩余数量"，但生成的命令**把原题整段塞回给工具**，没有利用子目标。

### 2.3 执行：切代码 + exec

```python
pattern = r'.*?execution\s*=\s*tool\.execute\([^\n]*\)\s*(?:\n|$)'
```

实测三种写法：

| 模型代码 | 切出的块 |
|---|---|
| `execution = tool.execute(query="a")` | 1 块 |
| `x = 48*3/8` + `execution = tool.execute(...)` + `print(x)` | 1 块，**含前两行**，`print(x)` 丢 |
| 只有 `def f(x): return x` | **0 块**，什么都不执行 |

真实结果：

```json
[{"printed_output": "Number of books left: 18.0",
  "variables": {"initial_books": "48", "books_sold_monday": "18.0", ...},
  "execution_code": "..."}]
```

失败案例（Iceland 题）：

```json
[{"error": "unexpected indent (<string>, line 24)"}]
```

以及"跑了但没算"：

```json
[{"printed_output": "", "variables": {"is_prime": "<function: is_prime>"}}]
```

## 3. Verifier

### 3.1 输入

```text
Task: Evaluate if the current memory is complete and accurate enough to answer the query...
Context:
- **Query:** ...
- **Available Tools:** ...
- **Toolbox Metadata:** ...
- **Initial Analysis:** ...
- **Memory (Tools Used & Results):** {'Action Step 1': {...}}
Final Determination:
- If the memory is sufficient ... conclude with "STOP".
- If more information is needed ... conclude with "CONTINUE".
```

### 3.2 输出

期望：`MemoryVerification{analysis: str, stop_signal: bool}`
实际（qwen-plus 文本）：一大段分析 + 一句结论。

### 3.3 解析：STOP 到底怎么来的

```python
pattern = r'conclusion\**:?\s*\**\s*(\w+)'
...
if 'stop' in response.lower(): return analysis, 'STOP'
elif 'continue' in response.lower(): return analysis, 'CONTINUE'
```

实测 AMC 那题，verifier 输出：

```text
### Conclusion:
Since all parts of the query have been addressed...
**Final Determination: STOP**
```

解析过程：正则先命中 `Conclusion:` → 取到 `"Since"`（不是 STOP）→ 再命中 `This conclusion ensures` → `"ensures"` → 正则失败 → **全文搜子串 `stop`** → 命中 `STOP`。

**这就是"是否可信"的实证**：结论不是从规定字段读出来的，是文本里恰好出现了 `stop`。反例：模型若写 "I would not stop here"，同样会被判 STOP（离线已验证）。

## 4. Generator（生成器）

代码里**没有独立的 Generator 类**，是 Planner 的三个方法：

| 方法 | 输入 | 输出 | 用途 |
|---|---|---|---|
| `generate_base_response` | 题目 | 直接答案 | baseline（不用工具） |
| `generate_final_output` | 题目 + memory | 长篇详解 | 人看 |
| `generate_direct_output` | 题目 + 审题 + memory | 简洁答案 | **benchmark 打分用** |

实测 direct 输出（书店题）：

```text
**Process Summary:**
1. Initial Book Count: 48
2. Books Sold on Monday: 3/8 × 48 = 18
...
**Answer:** The bookstore has 18 copies left.
```

**两个要点**：
1. Generator 在循环之外，**无条件执行**——哪怕循环是因为 `max_steps` 耗尽（不是 STOP），它也会写答案；
2. 它只看到 memory，看不到 verifier 的意见，所以会把错误记忆当事实总结（Iceland 题编出了 `547 × 398783 = 216646961`）。

---

## 5. Memory：模块之间唯一的载体

```python
action = {
    'tool_name': tool_name,
    'sub_goal': sub_goal,
    'command': command,
    'result': result,
}
```

**只有四个字段**。因此：

- Planner 看不到 verifier 的 analysis（没存）；
- Planner 看不到 executor 的 analysis/explanation（没存）；
- Planner 看不到自己的 justification（解析时丢了）。

## 8. 结论

1. **作者 planner 在本复现中没有表现出可测量的优势**：AIME 10 题 6 vs 5、AIME 20 题 8 vs 8、多跳 13 vs 11、B 组 41 vs 41。所有差异都在 1–2 题内，样本量下不显著。
2. **决定成败的是"执行器会不会写工具调用"**：全底座 0/10、全作者 0/10，一旦把 executor 换成能干活的模型（qwen-plus），两组都跳到 5–6/10。这是本次实验最大的单一变量。
3. **Verifier 不可信**：它的结论靠正则/子串兜底，实测出现过"靠 `stop` 子串命中"判定；且它的 analysis 不进入下一轮，无法纠正 planner。
4. **Planner 的输入严重冗余**：7,272 字符里 98% 是模板、审题和工具说明书，题目只占 110 字符；历史每轮全量重放，越跑越贵。
5. **图像能力是死代码**：`is_multimodal` 默认关、引擎构造时硬编码 `False`，带图题目反而会让审题结果变成错误字典。

## 9. 与论文的差距来自哪里

| 差异 | 论文 | 我们 |
|---|---|---|
| planner | 训练后的 7B | 同（作者权重） |
| executor / verifier / generator | qwen2.5-7b-instruct | qwen-plus（无权限） |
| 工具 | Google 搜索 + Wikipedia + Python + Generalist | Wikipedia + Python + Generalist（缺 Google） |
| 评测 | 全量 benchmark + 官方评分脚本 | 10–20 题子集 + 宽松匹配 |
| 训练 | Flow-GRPO | **未训练** |

所以：**目前的数字不能用来否定论文**，只能说明"在官方执行器缺席、工具链残缺、样本很小的条件下，训练版 planner 与底座 planner 打平"。

## 10. 局限（必须写进汇报）

1. **没有训练**，只评测作者权重；
2. 单卡 24G，无法同时部署 planner 和官方执行器，用 qwen-plus 代替 qwen2.5-7b-instruct；
3. 缺 Google 搜索（Gemini key 随 Google 账号停用），搜索类数据集只能用维基；
4. 样本 10–20 题，置信区间宽；
5. OpenAI 依赖本机反向隧道，稳定性受限；
6. fp32→bf16 是我们自己转的，已验证 339 个 key 全齐、dtype 正确；
7. 评分器是宽松匹配（子串/字母），非官方脚本。
